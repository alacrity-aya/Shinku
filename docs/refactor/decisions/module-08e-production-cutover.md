# Module 8E eBPF Production Cutover Decisions

Design review findings and the ordered grill queue are recorded in [Module 8E Design Review Findings](module-08e-design-review-findings.md). The review gate is separate from the confirmed decisions below; unresolved findings must be settled before production implementation.

## Segment 20: Module 8E eBPF Production Cutover

Decisions:

1. XDP completes Query Eligibility before performing any cache lookup or Pending Query mutation. Every ineligible Query returns `XDP_PASS` with zero cache lookup and zero Pending side effects; an eligible Cache Hit performs one cache lookup and no Pending mutation, while an eligible Cache Miss performs one cache lookup and then attempts one Pending create or refresh. Pending retention failure remains Fail-open and returns `XDP_PASS`. The 19 generated Query Eligibility vectors verify these side effects rather than treating the XDP return code as the complete oracle.
2. An eligible Query is parsed exactly once into one shared bounded result. Cache lookup and Pending creation consume the same Header and Question facts; neither path reparses QNAME, QTYPE, or QCLASS independently. The result contains the physical Cache Key facts and the shared keyed 128-bit Question fingerprint selected by the Pending value decision. Duplicate parsers and independently calculated Question identities are rejected.
3. The MVP trusts the Downstream DNS Forwarder not to concurrently reuse one complete IPv4/UDP network tuple plus DNS Transaction ID for different Questions. Pending Query identity therefore uses one Query-oriented physical key containing Query source IPv4 and UDP port, Query destination IPv4 and UDP port, and Transaction ID, all in network byte order with explicit zeroed padding. XDP constructs that orientation directly; TC reverses the Response tuple to reproduce it. The key contains no ifindex, protocol discriminator, Question identity, or duplicated Cache Namespace. Query destination is the authoritative DNS Service Endpoint from which Cache Namespace is derived. An abnormal concurrent tuple-plus-ID reuse may lose one Cache Fill opportunity, but Question comparison before consumption prevents it from authorizing a mismatched Fill.
4. A Pending Query value proves Question identity with the existing keyed 128-bit fingerprint over the canonical QNAME, QTYPE, and QCLASS. It uses the same per-process secret and shared `shinku_ebpf_cache_fingerprint()` implementation as the physical Cache Key, but excludes Cache Namespace because the Pending key already identifies the authoritative DNS Service Endpoint. XDP computes the fingerprint once for both Cache lookup and Pending creation; TC computes it from the Response Question before attempting consumption. A mismatch leaves an Active record live. The accepted residual collision risk is the same cryptographic assumption as ADR-0015; storing and comparing the complete canonical Question is rejected because it adds up to 255 bytes per Pending value and another bounded Data Plane comparison without a material safety gain. The combined XDP/TC production path must pass a verifier load test on the MVP development host during implementation. Verifier rejection reopens this representation; it must not trigger a weaker fingerprint or runtime fallback.
5. A Pending Query value is exactly the 16-byte Question fingerprint followed by one naturally aligned 64-bit atomic `state_and_last_seen_ns`, for a 24-byte value with compile-time size, alignment, and offset assertions. Its high bit is `Claimed`; the low 63 bits hold the most recent `bpf_ktime_get_boot_ns()` value. An Active retransmission refresh and a matching Response claim each use a 64-bit compare-and-swap on that whole word, so refresh versus claim has one linearization order and at most one concurrent Response obtains Cache Fill authorization. A CAS loser rereads the current word and may retry only through a verifier-approved fixed bound; it never overwrites a Claimed value. If boot time cannot fit in 63 bits, Pending creation, refresh, and authorization Fail-open. Separate atomic time and state fields and `bpf_spin_lock` are rejected. This decision establishes data-plane claim ownership; decision 28 defines the accepted post-claim tombstone lifetime, and decision 29 defines the intentionally Fail-open cleanup race. The atomic operation, alignment, bounded retry, and combined production paths must pass verifier load tests on the production HASH map during implementation; rejection reopens this synchronization design.
6. The MVP production Pending map is bounded `BPF_MAP_TYPE_HASH` with decision 29's bounded Host cleanup. This is a deliberately conservative MVP choice, not a claim that HASH is globally optimal. `BPF_MAP_TYPE_LRU_HASH` is not a second production map and `PERF-8E-1` is no longer an 8E map-selection gate. LRU automatically evicts Active records and Claimed tombstones before Pending Query Timeout under capacity pressure; early tombstone eviction can permit same-key recreation followed by a duplicate old Response and another Fill. Reopening LRU therefore requires both evidence that HASH cleanup materially harms correlation, sweep progress, or CPU and an explicit decision to relax or otherwise protect that semantic boundary before any comparison. The selected HASH cleanup deliberately accepts only a narrower refresh/delete race whose outcome is a lost Fill with forwarding preserved; it never treats pressure-driven duplicate Fill as equivalent. The paused benchmark backlog is not revised by this decision, while required whole-system evidence under `PERF-M8-1` remains unchanged.
7. TC performs every fallible event-preparation step before claiming a matching Active Pending Query. After packet-envelope and Question validation, it looks up and checks the Pending value, reserves an unpublished ring record, and copies the complete validated DNS payload into that reservation. It then uses compare-and-swap to transition the observed Active state/time word to Claimed. Reservation or copy failure discards the reservation without changing Pending state; CAS failure also discards it, so only the claim winner submits an event and duplicate Responses may do bounded speculative copy work but cannot authorize duplicate Cache Fills. After a successful CAS, TC submits the already complete event; ring submission has no recoverable failure result and the Response path does not delete the Claimed record. Claim-before-reserve with rollback and permanent consume-before-reserve are rejected because they add a wider authorization state machine, can lose a concurrent retransmission refresh, or lose retryable Fill opportunities under ring pressure. Decision 28 retains the Claimed record as a tombstone until timeout cleanup, while decision 29 accepts a possible cleanup race only as a lost Fill. The production path owes verifier, ring-pressure, concurrent retransmission, duplicate-Response, cleanup-race, and same-key reuse tests; exact event framing remains decision 8E-6.
8. The correlated packet-ring ABI is one fixed 528-byte `ebpf_correlated_dns_event`: a native-endian 64-bit BOOTTIME `response_observed_at_ns`, network-order Query-destination IPv4 and UDP port, a 16-bit response size, and a 512-byte DNS Response array, in that order. Shared ABI assertions fix the header at 16 bytes and the complete record at 528 bytes with no implicit padding. After complete packet-envelope, Question, and live-Pending validation but before ring reservation, TC reads `bpf_ktime_get_boot_ns()` once as the Response Observation Time. TC reserves the complete fixed record with ordinary `bpf_ringbuf_reserve()`, copies only the validated `response_size` bytes, and deliberately does not clear the inactive tail. The complete raw callback span contains those unspecified bytes, but only the 16-byte header and `response[0..response_size)` are semantic event data. TC derives the complete active DNS payload from a consistent UDP Length and publishes only active lengths from the 12-byte DNS Header through 512 bytes. A larger, truncated, or length-inconsistent datagram is not reserved, claimed, capped, or published and remains Fail-open on the network path. The event carries no fingerprint, complete Pending key, ifindex, or Cache Entry metadata. Query destination transfers the authoritative Cache Namespace; the timestamp transfers the authoritative start of TTL residence and Host callback time must not replace it. Decisions 34 and 35 define aging, Store Admission, and same-key observation ordering; decision 37 defines the inactive-tail boundary. Variable dynptr reservations and multiple fixed size classes are rejected for the MVP because their helper/verifier or ABI complexity is not justified before fixed-record ring pressure is measured. `PERF-8E-2` accounts for fixed 528-byte speculative reservations without assuming tail clearing and includes duplicate Responses, ring saturation, callback progress, and dropped Fill opportunities; material evidence may reopen variable records later.
9. Query Eligibility, Cache lookup, Pending mutation, and Response correlation require an unfragmented IPv4/UDP datagram with one unambiguous complete-message boundary. Both the More Fragments flag and Fragment Offset must be zero; neither XDP nor TC handles even a first fragment containing the UDP Header. IPv4 Total Length must be at least IHL plus the UDP Header and 12-byte DNS Header, UDP Length must be at least the UDP and DNS Headers, and IPv4 Total Length must equal IHL plus UDP Length exactly. The frame or skb must cover the complete IPv4 Total Length. Link-layer bytes beyond IPv4 Total Length are permitted only as Ethernet padding and never enter the DNS payload. Any fragment, undersized field, IP/UDP disagreement in either direction, or captured-length shortfall has zero Cache lookup, Pending, claim, or ring-reservation side effects and remains Fail-open. Permitting UDP Length merely as a bounded prefix of the IPv4 payload and adding fragment correlation/reassembly are rejected because they create multiple message boundaries or cross-packet state without an MVP deployment requirement. Backend-specific packet-envelope tests cover both fragment flag forms, every length inequality, truncated capture, and accepted Ethernet padding.
10. The MVP Cacheable Query and correlated Response packet envelopes require an IPv4 Internet Header Length of exactly five, so the IPv4 Header is the fixed 20-byte form with no Options. Any Query with Options has zero Cache lookup or Pending side effects, and any Response with Options has zero Pending claim or ring-reservation side effects; both remain Fail-open. Applying the same restriction at XDP and TC keeps one symmetric envelope profile and prevents the Cache Hit Path from reflecting direction- or path-sensitive Record Route, Timestamp, Source Route, Router Alert, or unknown Option state from the Query into a generated Response. Allowing Options only on the Response is rejected because its marginal Fill coverage does not justify an asymmetric parser contract, and complete Option interpretation or response reconstruction is outside the MVP. Focused tests cover every bounded non-five IHL value and prove zero side effects.
11. Input IPv4 and UDP checksum validation is not part of the MVP XDP Query or TC Response envelope. Native XDP has no portable checksum-valid field in `xdp_md`, Generic XDP and veth may preserve software-offload state not represented in packet bytes, and TC egress may observe `CHECKSUM_PARTIAL` before the device completes transmission. Shinku therefore applies the already selected fragment, fixed-IHL, IP/UDP length, bounded DNS wire, Query Eligibility, keyed fingerprint, and Query Correlation checks without treating raw input checksum bytes as a Cache or Pending gate. This may let a checksum-invalid but otherwise eligible Query receive a Cache Hit where the ordinary stack would have dropped it; that compatibility trade-off is accepted for the MVP instead of adding a topology-dependent offload contract. A Cache Hit does not trust the Query's IPv4 checksum: after all header mutations it computes the mandatory checksum from scratch over the fixed 20-byte output Header. It writes a zero UDP checksum, which is valid only for the current IPv4 MVP and preserves the existing eBPF hot-path policy. IPv6 support must compute UDP checksum. Driver-specific checksum metadata and strict software input validation remain future packet-envelope extensions rather than runtime probing or mixed behavior in one MVP object.
12. The MVP Cacheable Packet Profile is untagged Ethernet only. An inline `802.1Q` or `802.1ad` tag at any depth makes a Query or Response Pass-through with zero Cache lookup, Pending, claim, or ring-reservation side effects. A supported Cache Point exposes one already isolated untagged L2 domain to Shinku; a shared VLAN trunk, including a device that strips tags into RX metadata before XDP, is outside the declared MVP envelope. The current parser behavior that skips up to two inline tags is deleted from the replacement path because VLAN identity is absent from Cache Namespace and the physical Cache Key: two isolated VLANs may reuse the same DNS Service Endpoint IPv4 and port, so merely preserving tags on `XDP_TX` cannot prevent cross-VLAN Cache Hits. Driver-specific VLAN metadata handling is likewise rejected without complete identity propagation. VLAN-aware caching is tracked as conditional feature `DF-12`; it must extend backend-neutral Cache Namespace semantics, every Backend key, Pending identity, correlated-event transfer, XDP response handling, and shared tests together rather than restoring a parser-only exception.
13. The eBPF MVP correlates only the fixed DNS service port and exact same-Cache-Point direction: XDP admits a Query only when UDP destination port is 53, source port is nonzero, and DNS `QR=0`; TC considers a Response only when UDP source port is 53, destination port is nonzero, and DNS `QR=1`. TC reverses the complete Response IPv4/UDP tuple and requires an exact Pending key match, including both addresses, both ports, and Transaction ID. A NAT, proxy, port translation, asymmetric observation, or any other tuple change suppresses only Cache Fill; it never authorizes partial matching or changes Cache Hit behavior, and forwarding remains Fail-open. Nonstandard DNS ports, source port zero, and protocol-like UDP payloads on other ports are Pass-through. Conntrack or proxy identity is deferred to `DF-5` and cannot weaken this packet-only proof in 8E.
14. XDP Query Eligibility requires an address envelope that can be reversed into one valid unicast Cache Hit. Both Ethernet source and destination must be nonzero individual addresses: the group bit in the first octet must be clear, which excludes multicast and the all-ones broadcast address. Both IPv4 source and destination must be nonzero, outside `224.0.0.0/4`, and different from the limited broadcast address `255.255.255.255`. A failure returns `XDP_PASS` before Cache lookup or Pending mutation. UDP destination port 53 does not imply these address properties; it excludes conventional mDNS and LLMNR ports but cannot make an arbitrary port-53 frame safe to reverse with `XDP_TX`. Directed-broadcast detection is intentionally absent because XDP has no backend-neutral subnet-mask fact. TC does not repeat these address-class checks: an exact reverse-tuple match already ties the Response IPv4 addresses to an eligible Query, and TC can only authorize Cache Fill rather than emit a reversed packet. Tests cover each rejected source and destination address class and prove zero XDP side effects.
15. A Cache Hit constructs a deterministic fixed-form IPv4 Header instead of inheriting client-controlled Query fields. Before packet mutation it constructs the complete output Ethernet/IPv4/UDP/DNS frame in per-CPU scratch: eligible addresses are reversed, IPv4 version 4, IHL 5, TOS zero, Total Length equal to 20-byte IPv4 Header plus 8-byte UDP Header plus active DNS Response length, Identification zero, Don't Fragment set, Fragment Offset zero, TTL 64, protocol UDP, mandatory IPv4 checksum recomputed from scratch, IPv4 UDP checksum zero, Query Transaction ID/Question semantics applied, and every retained TTL aged. Together this yields one atomic datagram no larger than 540 bytes for the 512-byte DNS bound. Decision 38 makes `bpf_xdp_adjust_tail()` the mutation commit boundary and then writes this complete scratch frame in one helper operation. Preserving Query DSCP/ECN, TTL, Identification, or fragmentation policy is rejected because those fields describe the client-originated request rather than the DNS Service Endpoint's Response and would let a client control generated Response network properties. The MVP assumes its supported untagged isolated L2 Cache Point carries a 540-byte IPv4 datagram without fragmentation; a lower-MTU deployment is unsupported rather than handled by generated fragmentation. Packet-vector tests vary every discarded Query field and require the same normalized output Header and recomputed checksum.
16. `EbpfBackend` owns the synchronous packet-event consumer together with the `DnsPolicy` and `EbpfCacheStore` that it composes. Packet-ring creation gives `EbpfNativeSession` a non-owning reference to that typed consumer for exactly the ring lifetime. `ProductionEbpfNativeSession` keeps libbpf's `void*` context and C callback trampoline private; when decision 36's bounded packet poll invokes the trampoline, it synchronously calls the borrowed consumer, which validates the event, classifies the Response, reads BOOTTIME Store Admission Time immediately before admission, and completes `CacheStore::store(candidate, observed_at, now)` before returning. The borrowed ring bytes and Policy scratch never escape that callback. No packet payload is copied into a queue, and the Session does not own Policy, Store, or Cache Fill orchestration. Backend shutdown must close the packet ring and end the borrow before destroying the consumer, Policy, or Store; exact partial-start and aggregate-release sequencing remains 8E-9. A fake Session may synchronously inject events through the same typed boundary so composition tests do not reproduce libbpf handles. An asynchronous queue is rejected for the MVP because it adds bounded-capacity, overflow, ownership, copy, and fill-latency policy already reserved for a future measured `FillWork` design.
17. The typed Session boundary delivers one callback-scoped `std::span<const std::byte>` containing the raw libbpf sample; `EbpfNativeSession` does not decode the correlated-event ABI or construct Cache domain values. One eBPF composition decoder owned outside the Session requires the sample size to equal the fixed 528-byte record, reads the 16-byte Header without assuming callback-data alignment or violating aliasing rules, validates the network-order Response size in `[12, 512]`, converts the network-order destination IPv4 and port into one host-order `CacheNamespace`, converts the native-endian BOOTTIME observation value into strong `CacheTime`, and exposes only the active Response prefix. The decoder is the only production consumer of the raw record. It does not read, compare, copy, hash, serialize, or forward the inactive tail, and no complete raw event reaches `DnsPolicy`, Store, logs, diagnostics, or operator-facing state. Decode failure does not invoke Policy or Store; how that diagnostic is surfaced remains 8E-10, but even future diagnostics may materialize only validated header fields and active bytes. Production and fake Sessions both deliver raw ABI bytes through this same decoder, so unit and integration tests exercise the actual framing and byte-order boundary. Session-side domain decoding and direct casting of callback memory to the shared C ABI struct are rejected because they either move Cache Fill knowledge into native resource ownership or disguise unvalidated bytes and alignment assumptions as a typed event.
18. `EbpfNativeSession` adds one idempotent `noexcept close_packet_ring()` operation whose sole purpose is to free the native packet ring and clear its non-owning consumer reference, thereby ending the callback borrow before the consumer can be destroyed. Normal stop and Runner-driven cleanup after any partial-start failure use the same Backend sequence: stop and join the cleanup worker if present, close the packet ring, destroy the event consumer and `DnsPolicy`, destroy `EbpfCacheStore` and the narrow `PendingQueryCleaner`, then call the existing aggregate Session `release()`. Aggregate release tolerates an already closed packet ring and retains responsibility for the log ring, XDP/TC detach, legacy clsact ownership, and skeleton/map/arena destruction. The Store and cleaner retain decision 39's non-owning resource loans and may be destroyed during the short interval in which XDP/TC remain attached because those programs access only still-live Session-owned BPF resources, not the destroyed Host wrappers; no Host cleanup or writer remains in that interval. Splitting native shutdown into fallible quiesce and storage-release state machines is rejected because detach failure would multiply partial-release states without adding a required safety property. Calling aggregate release before destroying Store and cleaner is forbidden because it invalidates their borrowed native resources.
19. The Backend-owned `CleanupWorker` borrows `CacheStore` and a separate narrow `PendingQueryCleaner`; it no longer asks `EbpfNativeSession` or a legacy bridge to perform expiry policy. The cleaner is an eBPF Backend composition object that borrows the Session-owned Pending map fd and implements decision 29's bounded Host lookup/recheck/delete protocol; it has no BPF cleanup program and does not claim cleanup ownership atomically. The single worker maintains independent deadlines for Cache Entry and Pending Query cleanup. Cache Entry cleanup retains the configured `cleanup_interval`; decision 31 derives the Pending deadline independently from Pending Query Timeout, and decision 32 fixes the MVP batch/cursor contract. Each dispatch performs at most one bounded batch, checks the stop token, and, when both collaborators report `more_work`, alternates them so neither immediate continuation can starve the other. Each Cache Store batch reads fresh `CLOCK_BOOTTIME` and converts it at one eBPF-private composition point into strong `CacheTime`; Pending cleanup uses the same clock domain for candidate checks and accepts the documented refresh/delete race as a local lost-Fill outcome. Completion or a non-fatal error clears only that collaborator's immediate continuation and returns it to its own deadline without delaying an already-due peer. Stop requests interrupt deadline waits and are checked between every batch; Backend joins the worker before destroying either borrowed collaborator. Two cleanup threads and a Session cleanup entry are rejected because bounded fair dispatch does not justify another lifecycle and native resource ownership must not absorb expiry policy. A backend-neutral injectable Clock remains rejected because it hides the Backend-specific clock-domain invariant established by 8B.
20. `EbpfBackend::start()` completes every Host cache-composition step that can fail before attaching XDP or TC. It looks up the interface, computes the checked eBPF storage layout, creates the per-process fingerprint secret, builds decision 39's checked `EbpfSkeletonConfig`, and calls `prepare_skeleton(config)` to size maps, initialize `.rodata`, load the object, and return one move-only composite `EbpfNativeBinding`. Backend splits its narrow non-owning Cache and Pending loans into `EbpfCacheStore` and `PendingQueryCleaner`, constructs `DnsPolicy` and the synchronous event consumer, and creates the optional log ring. Only then does it execute the preserved XDP retry loop followed by the TCX-to-legacy-TC retry/fallback loop, create the packet ring borrowing the already-live consumer, and finally start the cleanup worker borrowing the already-live Store and cleaner. Store/cleaner allocation, Policy composition, secret generation, or log-ring failure therefore cannot expose a half-composed Data Plane on the interface. Attach failure and every later failure still leave cleanup owed to Runner-driven `stop()`, using decision 18's single idempotent unwind path. Constructing Host cache objects after attach and lazy construction on first poll/event are rejected because they move predictable startup failures into a live or runtime-only state. The accepted sequence intentionally retains the 8A XDP-before-TC and attach-before-packet-ring behavior; revising activation order would require separate evidence rather than being incidental to composition.
21. The private libbpf packet-sample trampoline always returns zero after dispatching a sample to the `noexcept` synchronous consumer. Exact-ABI decode failure, eBPF Cache Time read failure, and Cache Store failure abandon only that Cache Fill attempt; DNS Policy `Bypass` and Store `Rejected` are normal no-fill outcomes. None stops consumption of later samples in the same bounded batch, changes the `ring_buffer__consume_n()` result, increments a failure threshold toward Backend shutdown, or becomes `BackendError`. Reaching decision 36's 64-event limit completes the quantum successfully and is not an error or callback stop signal. Cleanup failure likewise abandons the current cleanup sequence and retries after the next configured interval without changing Backend lifecycle. Only a non-interruption error produced by packet-ring readiness wait or bounded consumption maps to `PollFailed`; log-ring error behavior is unchanged. This separates libbpf consumption control from Cache domain outcomes and preserves Fail-open forwarding even under indefinitely repeated Store or cleanup failure. ABI/time/Store/cleanup failures use the temporary diagnostic policy still to be selected in 8E-10, while Policy Bypass, Store Rejected, and successful Store outcomes remain silent. Returning nonzero from the sample callback for any event content, Cache operation, or normal batch limit is rejected because one event could abort later batch consumption and conflate content with scheduling.
22. Module 8E emits no runtime diagnostic for correlated-event ABI decode failure, Cache Time read failure, Cache Store failure, or cleanup failure. These conditions remain event- or batch-local Fail-open outcomes under decision 21, but before Module 10 they produce no `stderr` warning, log-ring record, counter, metric, status field, threshold, or operator-facing state. DNS Policy Bypass, Store Rejected, and successful Store outcomes are likewise silent. This is an explicit phase boundary rather than an assertion that the failures are unimportant: Module 10 will design the diagnostics/logging contract after both Backend boundaries stabilize, and `DF-8` separately governs any future Observability Surface. Per-event logging, a temporary rate limiter, and early metrics are rejected because they add hot-path blocking or disposable diagnostics infrastructure during the cutover. Tests observe these outcomes through injected fakes and state assertions, not production diagnostics.
23. Module 8E may build the correlated BPF path and Host composition incrementally behind standalone verifier, unit, and integration harnesses, but the production target performs one atomic Cache-path cutover. The cutover simultaneously selects the new XDP/TC program and ABI, replaces the Session's legacy bridge with the storage binding and typed consumer, moves cleanup to `EbpfCacheStore`, and removes the legacy parser/cache sources, build targets, tests, constants, and includes identified by the 8E-11 inventory. No runtime selector, Meson build option, compile-time fallback, production shadow path, or dual-write is introduced; the runnable daemon contains exactly one Cache Contract after the cutover, and source-control revert is the rollback mechanism. The legacy and correlated paths cannot form a meaningful dual-write comparison because they use different Query Correlation, Cache Key, ring event, arena publication, TTL, admission, and cleanup semantics, and running both would alter capacity, CPU, ring pressure, and races being measured. The final production switch therefore occurs only after the new path passes its independent harness gates, and legacy removal is part of the same 8E slice rather than a later cleanup promise.
24. The 8E-11 cutover uses strict semantic deletion rather than merely removing legacy objects from the production link. It deletes the complete old C cache/parser/bridge implementation (`cache_ops*`, `cache_recent.c`, `cache_segments.c`, `cache_sketch.c`, `cache_types.h`, `dns_parser*`, `hash*`, `loader_cache_bridge*`, and `parser_runtime.h`) and the obsolete shared `types.h` and `xdp_parser.h`; `constants.h` is deleted after its still-live values move to narrow owners. `cache.bpf.c` retains its build identity but is replaced by the correlated program. Tests whose only subject is the deleted Contract (`dns_hash_test.c`, `dns_parser_test.c`, `cache_store_test.c`, the legacy arena-slot `ring_buffer_test.c`, `dns_bench.c`, and `cares_expand_test.c`) and the now-orphaned c-ares dependency are deleted rather than kept as unbuilt reference code. The Meson `ecs` option and `SHINKU_ECS_ENABLED` plumbing are removed while the shared Query Eligibility vectors continue to require ECS Pass-through; `ebpf.arena_pages` is removed from Config, examples, generators, Session, fakes, and tests because the eBPF storage layout derives it. Existing benchmark code, integration/lifecycle/Cache Contract tests, `TESTED_FEATURES.md`, and current architecture, design, performance, or roadmap material have no preservation entitlement: retain and rewrite only the parts that directly test or describe the new MVP, and delete obsolete cases, harness code, and result artifacts. Historical ADRs and dated audits may continue to describe superseded code as history, but cannot be cited as the current Contract. Source control is the only archive for deleted implementation. Deferring semantic cleanup to Module 11 or retaining a dormant source/test archive is rejected because either leaves the repository expressing two contradictory Cache Contracts after the atomic production switch.
25. Module 8E correctness acceptance is Contract-complete but deliberately layered. Generated vectors and unprivileged unit tests prove DNS Policy, Store, correlated-event decoding, Cache Time boundaries, and injected Host failure behavior. Privileged BPF program tests prove Query Eligibility side effects, Pending creation/refresh/claim/reclamation, Query Correlation, packet-envelope rejection, Cache Hit rewriting, duplicate handling, and controllable map/ring pressure. The network-namespace suite proves only behavior that depends on the real cross-layer Operational Loops: startup and attach, miss through TC correlation and synchronous Host Fill to XDP Hit, Transaction ID and TTL patching, positive/negative/CNAME replay, Cache Namespace isolation, expiry, representative Pass-through, restart, signal handling, detach, and shutdown. Deterministic concurrency, ring saturation, map failures, and same-key recreation remain in controllable harnesses instead of being forced into timing-sensitive namespace tests. Every accepted Contract behavior must map to at least one deterministic proof, while every critical cross-layer workflow must also have an end-to-end proof; a single smoke flow and an end-to-end-only suite are both rejected. Decision 41 places all required correctness evidence on the current MVP development host and excludes CI design from Module 8.
26. Module 8 is a rewrite against the accepted Cache Contract, not an equivalence migration from the legacy implementation. Legacy behavior, unit tests, performance tests, benchmark harness details, and recorded numbers therefore create no acceptance baseline and may be discarded; an artifact survives only when a concrete part is useful after being rewritten for the new system. In particular, the historical 425K-QPS and latency report does not impose an absolute target, and 8E does not build or run the deleted implementation merely to establish a relative regression threshold. Correctness is judged only against decisions 1 through 25 and their generated contracts. New-system performance evidence is defined intrinsically without a legacy comparison, while decision 42 fixes synchronous Fill for the MVP.
27. Module 8 requires reproducible new-system performance evidence but does not set a product-performance pass line before a target hardware class or QPS, latency, and CPU SLO exists. `PERF-M8-1` measures the DNS service with its native cache disabled and enabled, the service with Shinku, and the combined native-cache-plus-Shinku case under one fixed topology, dataset, CPU allocation, warmup, duration, run count, and correctness criterion. It records QPS, p50/p99, DNS-service CPU, Shinku CPU, packet loss, Cache Hit ratio, response correctness, dispersion, and the complete environment. Incorrect Responses, forwarding loss, or failure of the packet ring to make sustained progress are correctness or Operational Loop failures and block completion; the observed QPS, latency, Cache Hit ratio, Fill loss, and CPU values otherwise establish the first new-system baseline rather than pass or fail against legacy or an arbitrary uplift. The benchmark must run and its artifact must be recorded before Module 8 performance evidence is complete, but low improvement, limited Fill throughput, or ring-pressure Fill loss alone does not block the 8E production cutover or trigger asynchronous Fill. Omitting performance evidence and inventing a fixed improvement over one DNS service are rejected. Decision 42 fixes synchronous Fill for the MVP; any later asynchronous design is a separate post-MVP decision.
28. After TC successfully claims a matching Response and submits its correlated event, the Pending Query remains `Claimed` as a consumed-exchange tombstone until its existing Pending Query Timeout elapses and cleanup reclaims it. The Response path never deletes it after submit. XDP encountering the tombstone does not refresh, overwrite, or reactivate it, so a late Query retransmission cannot recreate an Active record that a duplicate old Response can claim; TC encountering it cannot authorize another Fill. This deliberately spends Pending Capacity and suppresses a genuinely new same-key exchange until timeout in exchange for one-Fill-per-exchange semantics and removal of response-path post-submit deletion ABA. Bounded ordinary HASH with Host cleanup is the production representation. LRU is rejected for the MVP because automatic eviction can remove the tombstone before timeout and reopen duplicate Fill; reconsidering it requires an explicit semantic decision rather than a performance-only substitution. Decision 29 defines cleanup reclamation.
29. Pending cleanup uses bounded Host-side map operations against the production `BPF_MAP_TYPE_HASH`; it does not load a separate BPF reclaimer. The cleaner obtains a bounded batch of key/value snapshots, treats only records whose snapshot may be past Pending Query Timeout as candidates, and performs one immediate lookup/recheck before deleting each candidate. An expired Claimed tombstone is immutable on the data plane, so deleting it after the recheck is safe. An expired Active record may race with an XDP refresh between the recheck and delete; this accepted race can remove a newly refreshed Pending and lose one Cache Fill, but it cannot authorize a mismatched Response, create an incorrect Cache Entry, or affect DNS forwarding. The cleanup result remains local Fail-open, and the next sweep handles any retained stale state. Response-path deletion remains forbidden, so the old same-key post-submit ABA is absent. A kernel-side CAS reclaimer, per-entry `bpf_timer`, and unconditional first-read delete are rejected: the first two add disproportionate verifier/resource complexity, while the last widens the race unnecessarily. Deterministic tests must cover refresh-before-recheck, refresh-after-recheck, duplicate Response, claimed tombstone deletion, delete failure, bounded cursor continuation, and forwarding preservation. Decision 30 defines ownership, decision 31 defines cadence, and decision 32 defines the batch/cursor contract.
30. One Backend-owned `CleanupWorker` owns scheduling for both Cache Entry and Pending Query cleanup. It borrows two independent collaborators: `CacheStore` for Cache Entries and a narrow `PendingQueryCleaner` for decision 29's bounded map operations. The cleaner borrows the Session-owned Pending map fd but owns Pending expiry composition; `EbpfNativeSession` remains a resource boundary and exposes no cleanup-policy operation. The worker maintains independent deadlines, dispatches at most one decision-32 batch at a time, checks stop between batches, and alternates collaborators when both report `more_work`, so neither immediate continuation starves the other. A completion or non-fatal error resets only that collaborator to its own deadline. Startup constructs both collaborators before attach and starts the worker only after packet-ring creation; shutdown joins it before destroying either collaborator and before aggregate Session release. A second cleanup thread and Session-owned cleanup are rejected because fair bounded dispatch preserves isolation without another lifecycle or a policy-bearing native boundary. Decision 31 defines Pending cadence.
31. Pending Query cleanup uses an independent normal deadline equal to one half of the configured Pending Query Timeout; it does not reuse the Cache Entry `cleanup_interval` and adds no `pending_cleanup_interval` setting. Thus the normal first cleanup opportunity after expiry is targeted within another half-timeout, excluding time needed to complete bounded scan continuations. Checked configuration/composition must reject or otherwise make unrepresentable any positive timeout whose halved native duration would be zero; the worker does not busy-loop or introduce a special runtime floor. Cache Entry cleanup continues on its existing independently configured deadline. After a Pending pass completes or fails non-fatally, its next deadline is one half-timeout later; `more_work` uses decision 30's immediate fair continuation rather than resetting the deadline. Tests cover the supported minimum duration, odd duration rounding, independent Cache/Pending deadlines, delayed wakeup, error reset, and stop during the wait. Reusing Cache cleanup cadence and adding a separately tunable Pending interval are rejected because they respectively allow timeout-independent stale occupancy or expose an unnecessary and potentially inconsistent MVP setting. Decision 32 defines the work quantum.
32. The MVP `PendingQueryCleaner` inspects at most 256 Pending records per batch using `bpf_map_lookup_batch()` and a persistent opaque batch cursor. The count bounds inspected snapshots, not successful deletions. A null input cursor begins a sweep; a nonterminal result persists the returned cursor and reports `more_work`; the terminal result processes its returned records and resets the cursor so the next scheduled sweep starts from the beginning. An error other than normal end-of-map abandons the current sweep and resets it for the next Pending deadline. Concurrent map mutation may cause a sweep to omit or revisit a record because the batch is not a consistent snapshot; correctness does not depend on sweep completeness, and the next scheduled sweep repairs retained stale state. Each candidate still follows decision 29's immediate lookup/recheck/delete protocol. After every batch, the worker checks stop and applies decision 30's fair Cache/Pending rotation. The fixed 256 constant is an MVP choice, not a user setting or a claim of optimality. Implementation evidence reopens it if a production-shaped workload shows persistent inability to complete sweeps, material cleanup-induced correlation loss, or unacceptable stop/Cache-cleanup delay; otherwise no adaptive or time-budgeted policy is added.
33. Cache TTL residence begins at TC Response Observation Time, not at Host ring consumption or Store Admission. After complete Response envelope, Question, and live-Pending validation and before reserving the event, TC captures one 64-bit `bpf_ktime_get_boot_ns()` value and publishes it as native-endian `response_observed_at_ns` in decision 8's 528-byte event. The Backend decoder converts that value into the same strong BOOTTIME `CacheTime` domain used by Store, cleanup, and XDP Cache Hits; it never substitutes callback time. This absolute 64-bit timestamp is chosen over Host-only admission time, which extends TTL by ring delay, and over a truncated timestamp, which adds wrap and precision rules to save four bytes. The internal TC-to-Host path is trusted to preserve representable BOOTTIME ordering; decisions 34 and 35 define lifetime exhaustion, TTL aging, the Store API, and same-key monotonicity.
34. `CacheStore::store()` receives three inputs: the unchanged `CacheCandidate`, its strong `Response Observation Time observed_at`, and a strong `Store Admission Time now` read from `CLOCK_BOOTTIME` immediately before the call. `CacheCandidate` remains free of Backend time. The trusted internal chain guarantees a positive `uint32_t`-derived lifetime, complete bounded Response/TTL plan, nonnegative representable BOOTTIME values, and `observed_at <= now`; Store does not repeat those validations. It rejects only when `expires_at = observed_at + lifetime` is less than or equal to `now`, which is the normal case where ring/Host delay exhausts the entry before admission. On admission it persists `stored_at_ns = observed_at` and `expires_at_ns = expires_at`, so the existing XDP rule that rounds every RR's remaining TTL down from `hit_time - stored_at_ns` automatically includes ring and Host processing delay without rewriting borrowed Response bytes. Store evaluates whether a selected victim is expired against `now`, not `observed_at`; an expired victim therefore yields `Inserted` according to the existing Store Outcome contract. Pre-aging only the Candidate lifetime, copying and patching all TTL bytes in Host, and letting Store read its own clock are rejected because they respectively age only the minimum TTL, duplicate the Cache Hit patch path, or violate the explicit Backend clock-domain boundary. Decision 35 adds same-key monotonicity.
35. Same-key Store Admission is monotonic in Response Observation Time. After locating an existing Cache Publication and before copying rollback bytes or mutating its slot, Store reads the existing `stored_at_ns`; if `incoming observed_at <= existing stored_at`, it returns normal `StoreOutcome::Rejected` without changing the slot, map publication, owner metadata, generation, or replacement cursor. Only a strictly later observation may perform the existing in-place `Updated` path. The rule applies even when the existing entry is expired at admission or the older incoming Candidate would have a later expiry: once a newer Response has been observed, the Cache does not regress to older content merely to recover a Fill or retain a longer TTL. Equal timestamps use first-published-wins because they provide no ordering proof and rewriting would add no freshness guarantee. Host ring-consumption order and greatest-expiry selection are rejected because they can let an older Response overwrite newer observed content. Tests cover older, equal, and newer observations, expired existing entries, different lifetimes, and proof that rejection leaves publication and replacement state unchanged.
36. One `EbpfBackend::poll()` synchronously consumes at most 64 packet-ring events. It first drains the optional log ring with a zero timeout; the diagnostic ring must never inherit the packet timeout. `EbpfNativeSession::poll_packet_ring(timeout_ms)` first calls `ring_buffer__consume_n(packet_ring, 64)` without blocking; a positive result returns immediately. If it consumes zero, Session waits up to `timeout_ms` on `ring_buffer__epoll_fd(packet_ring)` and, when ready, calls `ring_buffer__consume_n(packet_ring, 64)` once more. Readiness timeout and interruption complete the quantum successfully; any other readiness-wait or consume error maps to `PollFailed`. A result in `[0, 64]`, including exactly 64 with backlog remaining, is successful; neither Session nor Backend probes whether more events remain. Control returns to `BackendRunner`, which checks Stop Condition before the next Backend poll. The sample callback remains always-zero and no batch-limit lifecycle result is added. ADR-0047 later removes the binary activity result entirely. The fixed 64-event quantum is an internal MVP constant rather than configuration. Tests cover already-ready backlog without waiting, empty wait timeout, readiness followed by consumption, exactly 64 with sustained producers, wait/consume interruption and errors, a Stop Request after a full batch, and cleanup-worker join while callbacks are active. Callback-return batching and a separate consumer thread/queue are rejected because they respectively overload content callback semantics or reopen asynchronous ownership and saturation policy.
37. The inactive suffix `response[response_size..512)` in a fixed correlated event has unspecified bytes and is present in the raw 528-byte libbpf callback span; it is not claimed to be unexposed or zero. TC performs no full-tail clearing. Only the validated 16-byte header and active Response prefix are semantic data. The Backend decoder must be tail-independent and is forbidden to read, compare, copy, hash, serialize, log, diagnose, or pass the suffix to Policy or Store; future observability must materialize validated fields and active bytes rather than export the raw record. Production and fake tests poison the inactive suffix with different patterns and require identical decode, Policy, Store, and outcome behavior, while a raw-boundary test confirms that the callback span itself may contain the poison. This matches the fixed-stride Cache Entry rule from 8D and avoids a fixed 512-byte clearing cost, including for speculative reservations later discarded after CAS loss. Full clearing and variable-length/dynptr records are rejected for the MVP because the active-length boundary already supplies safety and their bandwidth or verifier/ABI cost is not justified. Reopening raw event export or cross-process delivery must first reopen this information-boundary decision.
38. `bpf_xdp_adjust_tail()` is the Cache Hit packet-mutation commit boundary. Before calling it, XDP completes every lookup, slot snapshot and generation check, time/expiry check, TTL patch, output-length calculation, MAC/IP/UDP/DNS construction, and checksum calculation into one complete per-CPU scratch frame. Any failure before or at `bpf_xdp_adjust_tail()` returns `XDP_PASS`; an adjust failure is treated as leaving the original Query suitable for the ordinary path. After a successful adjust, XDP re-derives and bounds-checks packet data as required by the verifier and invokes exactly one `bpf_xdp_store_bytes()` to replace the complete frame. Store success returns `XDP_TX`; store failure returns `XDP_DROP` because the resized Query is no longer safe to forward. No post-adjust path returns `XDP_PASS`, and no incremental packet mutation or rollback protocol is attempted. This is a deliberate fail-closed exception after commit, limited to one already-mutated Query, rather than a general weakening of Fail-open Cache miss/error behavior. The combined production path must pass verifier/load tests for maximum frame length and variable active length. Program tests inject or model adjust failure, post-adjust bounds failure, final store failure, and success, requiring respectively `PASS`, `DROP`, `DROP`, and `TX`, and prove that no partially constructed or resized packet reaches the ordinary stack. Direct variable packet-store loops and rollback are rejected because they respectively complicate verifier/auditability or introduce fallible reverse mutation.
39. Skeleton preparation uses one eBPF-private typed `EbpfSkeletonConfig` containing the checked `EbpfCacheStorageLayout`, per-process fingerprint secret, 32-bit Pending Query Capacity, and 64-bit Pending Query Timeout in nanoseconds. Backend derives it from validated Cache Config before load; checked conversion rejects any representation failure. `EbpfNativeSession::prepare_skeleton(config)` sets arena and Cache/Pending map sizes, writes only a fixed-width shared `.rodata` ABI with compile-time size/alignment/offset assertions, disables generated auto-attach as required, loads the object, maps the arena, and returns one move-only `EbpfNativeBinding`. That composite binding contains exactly a move-only `EbpfNativeStorageBinding` loan with cache-map fd and writable arena span plus a move-only `EbpfNativePendingBinding` loan with the Pending HASH fd. Both loans are non-owning: they do not duplicate or close fds, unmap memory, expose skeleton/program/link/ring handles, or carry Config, Policy, cleanup cadence, cursor, or Store semantics. Backend moves the Cache loan into `EbpfCacheStore` and the Pending loan into `PendingQueryCleaner`; Session remains sole native owner and is released only after worker, Store, and Cleaner destruction. Preparation failure returns no binding while Session retains partial resources for the existing Runner-driven release path. Separate post-load binding accessors, an expanding positional parameter list, and Backend manipulation of generated skeleton/libbpf objects are rejected because they permit invalid lifecycle access, obscure one coherent pre-load configuration, or split native ownership. Fake-Session and integration tests verify exact map capacity, timeout conversion and `.rodata` value, one-time loan splitting, invalid moved-from bindings, failure unwind, and borrower-before-owner destruction.
40. ADR-0003 remains a historical record of why the eBPF Backend must stay runnable, but Module 8E explicitly supersedes its unqualified requirement to preserve "existing eBPF tests." BPF build and skeleton generation plus the attach/detach, packet-ring polling, Cache/Pending cleanup scheduling, signal handling, and shutdown Operational Loops remain mandatory. Individual legacy implementations, tests, benchmarks, and recorded results have no preservation entitlement; retain or rewrite only material that proves the current Contract, and remove obsolete artifacts during decision 24's strict semantic cutover. ADR-0003 receives a prominent qualification and link rather than a rewritten historical rationale. Leaving the ADR conflict implicit is rejected because future readers could incorrectly treat legacy coverage as an active acceptance contract.
41. Module 8 MVP defines no CI execution matrix and does not require CI infrastructure. Completion requires every current-Contract test applicable to Module 8 to pass on the current development host, including generated-vector and unprivileged unit tests, BPF compilation and skeleton generation, production-program verifier/load tests, `bpf_prog_test_run_opts()` tests, root network-namespace integration, lifecycle and Operational Loop coverage, and the required soak and fuzz smoke runs. A privilege-dependent test that skips because it was run without the required privilege is not a passing completion result; it must be rerun successfully in the capable local environment. The recorded evidence identifies the host kernel, compiler/libbpf toolchain, commands, and results. `PERF-M8-1` remains separate required performance evidence under decision 27 and is not redefined as a correctness test. Requiring privileged CI, splitting completion between local and CI environments, and treating a skip as success are rejected for the MVP. A future CI design is outside Module 8 and requires a separate decision only when the project needs it.
42. Synchronous callback-local Cache Fill is the fixed Module 8 MVP Contract, not a provisional path awaiting a performance threshold. The packet-event consumer completes decode, Policy classification, Store Admission Time acquisition, and `CacheStore::store(candidate, observed_at, now)` before returning; Module 8 adds no `FillWork` pool, queue, payload copy, asynchronous consumer, saturation policy, or shutdown drain protocol. Required performance evidence records the synchronous system honestly, but low QPS, low Cache Hit ratio, limited Fill throughput, or ring-pressure Fill loss does not by itself trigger an 8E architecture change because the MVP has no product SLO. Incorrect Responses, forwarding loss, inability to stop cleanly, or failure of packet-ring polling to make sustained progress remain correctness or Operational Loop failures and must be fixed; evidence that one of those Contracts cannot hold may reopen the design. Any otherwise motivated asynchronous Fill design is a separate post-MVP decision with independently attributed evidence. Defining an arbitrary pre-SLO threshold and implementing asynchronous Fill immediately are rejected. The paused benchmark backlog is not revised by this decision.
