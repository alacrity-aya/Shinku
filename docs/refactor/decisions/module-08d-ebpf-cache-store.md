# Module 8D eBPF Cache Store Decisions

## Segment 19: Module 8D eBPF Cache Store

Decisions:

1. The eBPF Cache Store uses one fixed-capacity raw arena slab rather than a compile-time array of 512-byte `cache_entry` objects, multiple BPF object variants, or variable-size per-entry allocation. The slot stride is aligned and derived at startup from the resolved per-entry metadata layout plus `CacheConfig.max_response_bytes`; XDP and Host Runtime use the same checked `arena_base + slot_index * slot_stride` calculation. This gives every configured response limit in `[128, 512]` a corresponding density benefit without fragmentation. A minimal load/verifier prototype must prove runtime stride arithmetic before the full Store is implemented; if the target verifier rejects it, the decision is reopened rather than silently reverting to fixed 512-byte slots.
2. `ebpf.arena_pages` is removed from Config Schema. Arena page count is an implementation result derived from validated `CacheConfig.max_entries`, the resolved runtime slot stride, required arena control/alignment bytes, and the trusted host page size. The eBPF cache map is likewise sized to exactly `max_entries` before skeleton load. This removes two competing descriptions of Cache Capacity: operators configure logical entry capacity and response limit, while the Backend owns their physical page translation. The validated Config and fixed ABI bounds make the arithmetic representable; failures that depend on kernel map creation or mmap remain Backend `start()` failures.
3. The MVP physical Cache Entry uses a self-contained seqlocked arena slot. All metadata consumed by the Cache Hit Path, the complete TTL-offset plan, and the verbatim response bytes participate in one slot snapshot; the BPF hash-map value is a small Cache Publication handle containing only the slot index and generation. This avoids a second mutable metadata snapshot in the map while preserving in-place same-key Update. Exact timestamp fields and widths are resolved with the Cache Time decision. Immutable copy-on-write slots were considered because they simplify XDP reads, but safe reuse requires reader refcounts or an epoch/RCU/QSBR reclamation protocol; per-hit shared refcounts threaten hot-key scalability, while a new cross-boundary epoch subsystem is too large for the MVP. Retain immutable slots plus per-CPU QSBR as a documented future optimization to benchmark if seqlock validation or rollback becomes measurable.
4. Verifier feasibility is an entry gate for 8D implementation rather than an end-of-slice check. After choosing the fingerprint algorithm, focused BPF programs load-test the worst-case keyed fingerprint path and a complete 45-offset TTL patch loop independently. A third prototype load-tests the combined production worst path, including raw-arena runtime stride calculation, coherent slot validation, response construction, and TTL patching, because individually accepted helpers do not prove that their combined instruction, stack, state, and bounds complexity is accepted. Decision 14 resolves the MVP target and failure behavior.
5. The eBPF Cache Time Domain is elapsed boot time including system suspend: Host Runtime reads `clock_gettime(CLOCK_BOOTTIME)`, and BPF reads `bpf_ktime_get_boot_ns()`. This supersedes the legacy `CLOCK_MONOTONIC`/`bpf_ktime_get_ns()` pairing, which would pause DNS TTL consumption during suspend and could serve stale entries after resume. Both values are converted to unsigned nanoseconds at one Backend boundary and have no wall-clock meaning.
6. Each arena slot persists both `stored_at_ns` and `expires_at_ns`. XDP checks `now >= expires_at_ns` directly and computes per-RR aging from `now - stored_at_ns`; it does not reconstruct one value from a whole-second lifetime on every hit. The trusted TC/Policy path supplies ordered representable BOOTTIME and a positive `uint32_t`-derived lifetime, so Store computes timestamp addition directly. The two 64-bit fields also avoid a false space optimization because the slot header is aligned and both expiry and elapsed time are hot-path facts.
7. The eBPF physical fingerprint uses the SipHash-2-4 128-bit output variant over the Canonical DNS Name followed by question type and class. The network-order Cache Namespace remains plaintext in the physical map key. One shared `static __always_inline` implementation is compiled into BPF and Host Runtime and is covered by fixed official/reference vectors plus cross-boundary vectors. The MVP ships no alternate physical-key implementation. Verifier rejection on the development host reopens this decision; two domain-separated SipHash-2-4 64-bit outputs and the complete logical key remain design candidates rather than automatic or runtime fallbacks.
8. `EbpfBackend::start()` owns fingerprint-secret creation. It fills a typed per-process secret with `getrandom()`, handling interruption and short reads, and treats entropy failure as `StartFailed`; it never falls back to a constant, `std::random_device`, a Config value, or a persisted file. Backend passes the same value to `prepare_skeleton()` for pre-load `.rodata` initialization and to `EbpfCacheStore` construction. Unit and integration tests may inject a fixed secret through the existing Backend test seam; production never logs the value. Maps remain unpinned, so restart intentionally invalidates all previous fingerprints with the rest of the process-owned cache.
9. XDP obtains a coherent Cache Entry through a per-CPU scratch-map snapshot. It reads an even slot sequence, copies hit-visible metadata, the complete TTL-offset plan, and active response bytes from the raw arena into the current CPU's scratch value, then verifies matching sequence and generation and validates every copied bound. Until those checks succeed it does not resize or modify the Query packet, so a conflict can safely return `XDP_PASS`. Only a validated scratch snapshot is used for expiry, Response construction, Transaction ID and Question rebinding, and TTL aging. This costs one per-CPU map lookup and an additional bounded copy but avoids BPF-stack pressure, shared Reader writes, and the unsafe legacy behavior of returning `XDP_PASS` after partial packet mutation.
10. The eBPF Store uses an invalidate-first state machine with a rollback buffer allocated at Store construction and reused without allocation by `store()`. Same-key Update backs up and rewrites its existing slot under a new 64-bit generation, then updates the map handle as Cache Publication; failed publication restores the old slot so the old handle becomes hit-visible again. Replacement first removes the live victim key, then overwrites its slot and publishes the candidate. A failed candidate publication may leave that victim invalidated, which is explicitly permitted by the Store error contract, while the candidate never becomes visible. Empty or expired-slot failure returns the slot to free state. Owner records, free-list membership, and replacement cursor change only at their documented successful or rollback transitions.
11. MVP Store Admission uses free slots, including cleanup-reclaimed slots, before deterministic round-robin Replacement. Same-key Update remains in its current slot and does not advance replacement selection. Reusing an expired selected slot is `Inserted`; displacing a different hit-visible key is `Replaced`. The legacy minimum-TTL, recent dampening, frequency sketch, and hot/cold segments are deleted rather than inherited. `PERF-8D-1` in the benchmark backlog defines the later evidence required to adopt bounded CLOCK or a new TinyLFU-style policy.
12. One Store-owned mutex serializes the single Cache Fill caller and bounded cleanup caller across owner-index, free-list, replacement-cursor, BPF-map, and arena mutations. This satisfies the Cache Store concurrency contract without a Backend mutex and never enters the XDP Cache Hit Path. Cleanup batch duration stays bounded. `PERF-8D-2` records the workload and metrics that must show material contention before finer-grained or per-slot synchronization is considered.
13. MVP cleanup walks the capacity-sized userspace owner index with a persistent cursor and a fixed Store-owned slots-per-call bound. A cleanup sequence returns `more_work` until it has examined one capacity-wide sweep, while the worker supplies a fresh Cache Time to each continuation. Owner/map agreement is an internal invariant, so cleanup directly erases an expired owner's physical key; any erase failure, including unexpected absence, returns `CleanupFailed` and leaves the owner for a later schedule. Cleanup and Store mutation are serialized by the Store mutex. `PERF-8D-3` records the future comparison against a generation-filtered expiration min-heap.
14. The Module 8D verifier gate targets only the current development host for the MVP. It consists of separate keyed-fingerprint and worst-case 45-offset TTL-loop load tests followed by the combined production path, but the build ships one production BPF object and no automatic or runtime fallback. The verifier-approved combined form uses `bpf_loop()` callbacks for active arena snapshot copies and TTL patching, plus `bpf_xdp_load_bytes()` and `bpf_xdp_store_bytes()` for bounded XDP frame copies; direct nested bounded loops exceeded the development kernel's one-million analyzed-instruction limit. The gate passes on Linux `7.1.5-200.fc44.x86_64` with Clang `22.1.8`. These helper requirements become part of the MVP host envelope. If this selected path is rejected on a supported host, the physical-key or hit-path design is reopened before implementation proceeds. A declared multi-kernel development-time support matrix, with one selected production implementation rather than runtime object probing, is deferred as `DF-1` in the Deferred Feature Backlog.
15. The concrete eBPF Store test strategy is layered. Unprivileged tests execute the real `EbpfCacheStore` state machine over heap-backed arena memory and injected fake map operations so publication failure, rollback, replacement, cleanup, and concurrency are deterministic. Privileged verifier tests use real BPF maps and arena storage, the production XDP program, `bpf_prog_test_run_opts()`, generated Cache Hit vectors, physical-key ABI checks, coherent snapshot behavior, and Cache Time expiry boundaries. Network-namespace integration separately verifies real attachment, packet-envelope behavior, lifecycle, and traffic forwarding. Test-only inspection stays in adapters and injected map operations rather than production Store APIs.
16. `EbpfNativeSession` remains the native resource ownership module; deleting it would move skeleton, link, ring, legacy-TC, and dependency-ordered release mechanics into `EbpfBackend` or recreate the removed native-operations seam. Module 8D therefore uses a narrow borrowed `EbpfNativeStorageBinding`. Session remains the sole owner of the skeleton, BPF maps, arena mapping, links, and rings; Store neither duplicates map fds nor establishes a second arena mapping. Backend constructs Store only after successful skeleton preparation and destroys Store before Session release. The binding exposes storage facts only: Cache Policy, Store Admission, publication, rollback, owner-index, and cleanup algorithms remain outside Session. Exact fields and lifetime encoding are resolved by the following 8D design decisions.
17. `EbpfNativeStorageBinding` contains only the cache-map file descriptor and a writable byte span over the userspace arena mapping. It does not expose the generated skeleton, BPF program/link/ring handles, Cache Config, Cache Policy, or a copy of the storage layout. The binding is a physical-resource loan; the independently supplied layout explains how Store interprets those bytes.
18. The eBPF Cache module owns a pure, unprivileged layout calculation that converts validated `CacheConfig` plus host page size into one `EbpfCacheStorageLayout`. Backend computes it once before resource acquisition and passes the same value to Session skeleton preparation and `EbpfCacheStore` construction. Session does not derive Cache Capacity or slot structure, and Backend does not duplicate the arithmetic. The layout includes the resolved entry and response capacities, TTL-offset capacity, aligned slot stride, total arena bytes, and arena page count.
19. `EbpfNativeStorageBinding` is move-only but non-owning: moving it transfers the single Store-construction loan and never closes the map fd or unmaps arena memory. `EbpfCacheStore` retains the binding while Session retains ownership. `EbpfBackend` declares and resets its members so Store and CleanupWorker are destroyed before `EbpfNativeSession::release()`, including partial-start failure. No shared lifetime token or Store-to-Session reference is introduced. Unit tests assert the destruction/release order because the C++ type system cannot prove this cross-object borrowing invariant by itself.
20. `EbpfNativeSession::prepare_skeleton(layout, secret)` returns `std::expected<EbpfNativeStorageBinding, std::error_code>` directly after skeleton load has made the cache-map fd and arena mapping usable. There is no separate `storage_binding()` accessor and no output parameter. A preparation failure returns no binding while Session retains ownership of any partially acquired native resources for Runner-driven release.
21. `EbpfCacheStorageLayout` is a C++ startup value with checked arithmetic. A dedicated conversion writes the fixed-width XDP-required subset into a shared C `.rodata` structure before skeleton load. The shared structure uses explicit-width fields and has compile-time size, alignment, and field-offset assertions; Host-only page-count and total-byte facts do not enter the BPF ABI. Host and BPF layout representations are not independently calculated.
22. `EbpfCacheStore` depends privately on a narrow runtime-polymorphic `EbpfCacheMap` interface containing lookup, update, and erase operations. The production adapter invokes BPF map operations through the borrowed map fd; the in-memory test adapter models map contents and scripts deterministic operation failures. This is a real two-adapter test seam. Its virtual calls occur only on Cache Fill and cleanup and never on the XDP Cache Hit Path. Function-table plus `void*` context and template-based Store variants are rejected.
23. TTL-offset capacity is derived once by `EbpfCacheStorageLayout` from `max_response_bytes` using the protocol-safe upper bound formed from the DNS header, minimum legal Question, and minimum legal RR wire sizes. Every slot in one Store has that fixed configured capacity. The derivation is checked and covered at every supported response limit, including the 512-byte worst case of 45 offsets. The Store neither reserves 45 offsets unconditionally for smaller response limits nor uses per-entry variable allocation.
24. `EbpfCacheStore` does not repeat production validation of its internal binding and layout. The checked layout factory rejects arithmetic and representability failures, successful Session preparation is the only production source of a binding, and Backend composition is the only production Store construction path. Store construction uses debug assertions for a non-negative map fd, required arena alignment and extent, and layout consistency; release builds trust those internal composition invariants. Per-operation code trusts Cache Candidate semantic validity, validates only concrete layout capacity, and validates mutable slot contents where required for memory safety and concurrent-reader correctness. This avoids turning every internal invariant into a second operational error channel.
25. Each fixed-stride arena slot uses a packed-active-region ordering: fixed aligned Header, the actual contiguous verbatim Response bytes, alignment padding for `uint16_t`, then the actual TTL-offset values, followed by unused slot capacity. The offset-table address is derived from the already bounded `response_size`; XDP validates response size, TTL count, alignment arithmetic, and the final offset-table end against the configured slot stride before copying. The per-CPU scratch representation may retain fixed Response and offset arrays. This ordering keeps the active arena read and Store write sequential, preserves the stored Response as one contiguous DNS message with valid compression-pointer coordinates, and avoids placing the Response behind unused offset capacity. It does not create variable-size slots or change Cache Capacity. Interleaving Response chunks with offset metadata is rejected because locating metadata becomes self-referential without another directory and prevents one bounded contiguous Response copy.
26. The shared arena slot Header is one fixed C ABI structure used directly by Host Runtime and BPF: 32-bit sequence, 16-bit response size, 16-bit TTL-offset count, 64-bit generation, 64-bit stored-at nanoseconds, and 64-bit expires-at nanoseconds. In that order it occupies 32 bytes with naturally aligned 64-bit fields. Shared headers enforce compile-time size, alignment, and field-offset assertions. Cache Entry Kind, owner state, free-list links, replacement metadata, and other Store-private facts do not enter the shared Header.
27. The slot seqlock sequence remains 32-bit while the Cache Publication generation is 64-bit. Sequence detects only a write overlapping one bounded XDP snapshot, so wrapping would require an unattainable number of writes during that read interval; widening it adds no practical protection. Generation protects map-handle identity across slot reuse and retains the previously selected 64-bit space. Both fields are naturally aligned in the shared ABI.
28. Store writes only the active Header, contiguous Response, required alignment padding, and actual TTL offsets. It does not clear the remainder of a fixed-stride slot when a shorter Candidate replaces a longer entry. Inactive bytes are not part of the Cache Entry and are unreachable because XDP bounds every copy from validated response size and TTL count. Tests poison inactive tails and prove they are never emitted or interpreted. Full-slot clearing and differential tail clearing are rejected because they add write bandwidth and cache pollution without replacing bounds validation.
29. The shared BPF cache-map value is a 16-byte `ebpf_cache_publication` containing 32-bit slot index, explicit zeroed 32-bit reserved field, and 64-bit generation. It contains no response length, timestamps, TTL count, or other duplicated slot metadata. Host and BPF enforce compile-time size, alignment, and offset assertions, and every publication zero-initializes the complete value before assigning fields.
30. Cache Publication uses semantic BPF map update flags. A new Insert uses `BPF_NOEXIST`; same-key Update uses `BPF_EXIST`; Replacement deletes the live victim key before publishing the candidate with `BPF_NOEXIST`. This lets the kernel enforce the Store state machine's map assumptions. `BPF_ANY` is rejected because it could hide owner-index divergence, and delete-before-update is rejected because it would violate same-key rollback semantics.
31. `EbpfCacheStore` allocates generations from one mutex-protected 64-bit monotonic counter beginning at one. Zero remains invalid/unpublished. Every Insert, Update, and Replacement attempt that begins a candidate slot write obtains a new generation; unsigned wrap skips zero and continues at one without creating an operational error branch. A full `2^64` reuse cycle during one process lifetime is outside the physical operating envelope. Random generations and permanent failure at `UINT64_MAX` are rejected.
32. The XDP reader places every slot-derived fact inside one seqlock interval. After map lookup and slot-index validation it reads an even first sequence, applies the reader ordering barrier, compares slot generation with the publication generation, validates Header-derived bounds, copies the active Response and TTL offsets into per-CPU scratch, applies the second reader barrier, and requires an unchanged second sequence. Generation-before-sequence and a second map lookup are rejected because neither provides a coherent arena snapshot.
33. Cache Hit scratch is one entry in a `BPF_MAP_TYPE_PERCPU_ARRAY` whose value has fixed worst-case arrays for the 512-byte Response and 45 TTL offsets plus the copied Header. One production BPF object therefore supports all configured Response Limits while each CPU receives private writable scratch. The small per-CPU memory overhead is accepted to avoid BPF-stack pressure, shared-reader writes, and configuration-specific BPF objects.
34. XDP completes every potentially failing Cache Hit operation against the validated scratch snapshot before mutating the Query packet: expiry and elapsed-time checks, every TTL-offset bound, TTL aging, and preparation of the response regions. Only after those steps succeed may it resize and rewrite the packet, update lengths/checksums, and return `XDP_TX`. Snapshot conflict, expiry, malformed mutable slot data, or patch-plan failure therefore returns `XDP_PASS` with the original Query untouched. Copying into the packet before the second sequence read or validating offsets after packet mutation is rejected.
35. Host slot writes use one shared seqlock-writer helper over an aligned `std::atomic_ref<uint32_t>` sequence. The begin transition uses acquire-release ordering to publish odd/write-in-progress before later body writes; the end transition uses release ordering after Header body, active Response, alignment padding, and TTL offsets are complete. BPF uses the verifier-accepted acquire/read-once and reader-barrier form selected by the prototype. Plain `volatile` access is not the synchronization contract, and atomic and non-atomic Host accesses to sequence are not mixed. Privileged concurrent-update tests stress the resulting Host/BPF protocol on the MVP development host.
36. Cleanup scans at most 256 owner slots per `CacheStore::cleanup()` call. This is a private eBPF Store implementation constant rather than Config Schema. A capacity-wide sweep therefore completes through deterministic bounded batches, with `more_work` causing immediate worker continuation and a stop-token check between batches. `PERF-8D-3` may later justify changing the batch size together with the cleanup representation; the MVP does not add a clock-read budget or operator tuning field.
37. Host owner metadata and reclaimed-slot allocation use one capacity-sized `SlotRecord` array plus a Host-only intrusive singly linked free list. Each record stores physical key, generation, expiry, and `next_free`; nonzero generation means occupied, while zero means no owner. `next_unused_slot` directly allocates the never-used suffix, and `free_head` pops or pushes reclaimed and failed-publication slots in O(1). No separate reclaimed-index vector, occupied boolean, bitmap, or arena-resident free-list metadata is introduced. Central state-transition helpers maintain `Never used -> candidate write -> occupied` and `occupied/failed candidate -> free` semantics under the Store mutex.
38. Superseded by the trusted internal-call rule: `EbpfCacheStore` retains a private constructor and one `create()` factory, but creation directly returns its owned object and does not translate `std::bad_alloc` into `expected`. Startup allocation failure follows the existing process-level fatal exception boundary. Runtime `store()` and `cleanup()` remain `noexcept`, allocation-free, and contain no exception guards.
39. Owner/map agreement is an internal Store invariant, not a recoverable runtime state. The single Store mutex serializes every Host writer, XDP only reads, maps are unpinned and process-owned, and each kernel map operation is atomic. Cleanup therefore deletes the expired owner's key directly without a preceding publication lookup. A delete error, including unexpected absence, returns `CleanupFailed` and leaves the owner record unchanged; it does not reclaim or reconstruct state. Same-key lookup uses debug assertions for slot range and owner-generation agreement rather than a release-build repair path.
40. Same-key rollback scratch is an inline fixed-size `std::array<std::byte, kMaxEbpfSlotStride>` inside `EbpfCacheStore`, sized for the 512-byte Response and 45-offset worst case. It introduces no allocation or construction failure and copies only the old entry's active region. A layout-sized vector and borrowing a shared arena slot are rejected because the maximum saving is only a few hundred bytes while they add allocation or visibility complexity.
41. The MVP introduces no process-global or Backend-wide memory pool. CLI/Config parsing, standard-library objects, libbpf, kernel maps/mappings, and thread stacks have different allocators and lifetimes, while the intended Cache Hit, synchronous Cache Fill, and cleanup paths are allocation-free after startup. Store-owned startup allocations use normal C++ allocation and the process-level fatal exception boundary; the inline rollback scratch removes one runtime allocation entirely. A future asynchronous Cache Fill may add its own bounded `FillWorkPool` only if `PERF-8E-2` justifies that feature; DPDK packet memory remains the DPDK Backend's native pool concern.
