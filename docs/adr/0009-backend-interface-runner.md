# Backend Interface and Runner

Shinku will introduce a C++23 backend lifecycle interface in `src/backend/`. The public backend abstraction is a normal pure virtual `Backend` class with `probe()`, `start()`, `poll_once()`, and `stop()`. CRTP is not part of the public interface because backend selection is runtime-configured through the validated Config model; CRTP may be used later only as a private implementation helper if it removes real duplication.

`probe()` is a pre-start capability gate with no persistent side effects. It may inspect validated configuration and host capabilities, but it must not attach programs, create production maps, bind ports, reserve hugepages, spawn threads, start packet processing, or mutate process/global state. It returns `std::expected<void, BackendError>`: success means the selected backend is supported; unsupported capability, permission, wrong-config, and probe execution failures are all typed `BackendError` values with human-readable messages.

`BackendRunner` owns lifecycle sequencing for `Created -> Running -> Stopped -> Failed` and owns the runtime loop through `run(StopCondition&)`. Its public API only exposes `run()` and `state()`: `probe()`, `start()`, `poll_once()`, and `stop()` are runner-private implementation details. `probe()` remains part of the `Backend` lifecycle interface and is called by `BackendRunner`; backend creation does not perform host capability probing. `run()` is single-use per runner instance. Backend implementations own backend-specific resource actions only. `poll_once()` returns quickly and reports idle work as `PollStatus::NoWork`. `PollStatus` remains only `WorkDone` or `NoWork`; event counts and backend-specific work categories belong to future diagnostics/observability work. `stop()` is idempotent. Backend lifecycle virtual functions remain non-`noexcept`, but operational failures are reported through `std::expected`; throwing from a lifecycle hook violates the Backend contract. `BackendRunner` does not catch such exceptions. Its `noexcept` destructor performs one best-effort stop attempt when cleanup remains pending and discards the returned status; an exception escaping `stop()` during destruction therefore terminates the process. `BackendError` remains a small typed status: code, human-readable message, and optional `std::error_code` cause. Module 6 does not introduce a production `BackendFactory`; backend creation moves to the eBPF Backend Module once a real C++ eBPF backend exists.

`BackendRunner` is the only production lifecycle controller. `Backend` lifecycle methods are runner-owned implementation hooks: production composition code creates a concrete backend through the `make_backend(const Config&)` free function, transfers it to `BackendRunner`, and then drives lifecycle only through the runner.

`run()` returns `std::expected<ShutdownReport, BackendError>` so normal shutdown keeps the accepted `StopRequest`. `ShutdownReport` belongs to the runner API and is defined with `BackendRunner`; in the MVP it contains `StopRequest accepted_stop` and no backend-specific shutdown metadata. `StopReason` and `StopRequest` are defined with the `StopCondition` interface in `src/backend/stop_condition.h`; `StopCondition` has a virtual destructor and exposes non-const `std::optional<StopRequest> poll() noexcept`. `StopRequest` starts with only `StopReason reason`. For Module 7, `StopReason` starts with `Signal`, `Manual`, and `Timeout`: Signal means Process Control observed a supported termination signal; Manual means an in-process control source explicitly requested orderly shutdown; Timeout means a Stop Condition's configured runtime deadline elapsed. Timeout does not mean a backend poll timeout, loader-operation timeout, or backend failure. All three reasons produce normal successful shutdown when accepted. Module 7 does not add production Manual or Timeout Stop Condition implementations; it defines their semantics so adding such sources later does not change the runner result contract. If a stop request already exists before startup, `run()` returns `ShutdownReport` without starting the backend and sets the runner state to `Stopped`. If `run()` is called while the runner state is not `Created`, it returns `BackendErrorCode::InvalidState`. After startup succeeds, `run()` checks the `StopCondition` once before entering the poll loop. If stopping after an accepted stop request fails, `run()` returns `BackendErrorCode::StopFailed` and the runner state becomes `Failed`. If polling fails, `run()` does not poll `StopCondition` again; it preserves the original poll error locally, performs best-effort stop, and returns the original error without adding suppressed-error support in Module 7. Runner tests exercise only `run()` and `state()` as the public contract; fake backend traces verify the private hook sequencing.

`stop_reason_name(StopReason) noexcept` is the canonical reason-to-text conversion. `BackendRunner` construction remains `noexcept` and accepts a null backend; `run()` reports that invariant violation as `BackendErrorCode::InvalidState`. A runtime backend error fixes the runner outcome as `Failed`, so successful best-effort cleanup does not change the state to `Stopped`. The Module 7 composition root does not print a successful `ShutdownReport`; it exits with status `0` and leaves successful-shutdown diagnostics to the later Runtime Diagnostics/Logging Module.

Lifecycle outcome and cleanup responsibility are separate. `BackendRunner` keeps a private `backend_active_` flag whose precise meaning is that the runner entered the backend start boundary and has not yet completed a successful stop; it does not assert that the backend is currently `Running`. The flag is set immediately before invoking `Backend::start()` and cleared by successful `Backend::stop()`. After any start failure, the runner invokes `stop()` and the backend uses its encapsulated resource state to release whatever partial startup acquired. A backend with no acquired resources treats stop as a successful no-op. Successful cleanup after a start or runtime failure clears `backend_active_` but leaves public state `Failed`; the destructor therefore avoids duplicate cleanup. If start and the subsequent stop both fail, `run()` preserves the original start error, keeps state `Failed`, leaves `backend_active_` set, and neither replaces the error with `StopFailed` nor adds a suppressed error. `run()` does not immediately retry a failed stop. The destructor makes one additional best-effort stop attempt and proceeds regardless of its result. Passing a null backend causes `run()` to set state to `Failed` and return `InvalidState`.

**Considered Options**

- Use CRTP as the public interface.
- Use `std::variant` or type erasure for all backends immediately.
- Let each backend implementation maintain its own lifecycle state.
- Introduce a production factory before any concrete C++ backend exists.
- Keep `probe()` as a startup-only capability check and drive progress through a runner-owned synchronous loop.

**Consequences**

The first backend contract is small, testable, and independent of current eBPF loader shape. Runtime backend choice remains possible without forcing compile-time templates into the public API. A single runner prevents eBPF and DPDK lifecycle behavior from drifting. Startup must fail when the selected backend is unsupported; it must not silently switch backend or storage mode. Real eBPF wiring remains in the next module, so Module 6 can be validated with fake backend tests.
