# eBPF Backend Production Boundary

Module 7 will make `EbpfBackend + BackendRunner` the only production eBPF runtime path and will not keep `shinku_run_legacy_ebpf()` as a fallback. `EbpfBackend::start()` wraps the existing C loader setup and cleanup-thread startup through a private transitional `EbpfLoaderOps` function table, without migrating `src/core/loader.c` to C++, because this slice is about lifecycle ownership rather than rewriting the loader implementation.

`make_backend(const Config&)` is a free function that returns `std::expected<std::unique_ptr<Backend>, BackendError>`, reports selected-but-unimplemented DPDK as `BackendErrorCode::Unsupported`, and reports disagreement between `Config::backend` and `Config::backend_config` as `BackendErrorCode::WrongConfig`. Production code outside the `make_backend()` implementation does not directly construct `EbpfBackend`; eBPF-specific tests may directly construct it with fake loader operations. eBPF probing checks the legacy privilege baseline first, then interface existence, then BPF arena support with `libbpf_probe_bpf_map_type(BPF_MAP_TYPE_ARENA, nullptr)` when available. Each `EbpfLoaderOps` probe operation returns `std::expected<bool, std::error_code>`: `false` means the check completed with a negative conclusion, while `std::unexpected` means the check could not be performed. `EbpfBackend` maps negative privilege, interface, and arena conclusions to `PermissionDenied`, `WrongConfig`, and `Unsupported`, respectively; it maps probe-operation errors to `ProbeFailed` and preserves their error code as `BackendError::cause`. The production adapter converts a negative libbpf probe return into an operation error and may retain the raw return value in the message. Cleanup-thread startup failure is fatal because cleanup scheduling is a backend-critical Operational Loop. Setup failures map to `StartFailed` without exposing private C loader error codes. `BackendError::cause` is populated only when the source contract explicitly identifies an errno or error code: private loader sentinels and ambiguous mixed-domain negative values stay in the message with no cause, while an explicitly identified system error such as a `pthread_create()` result may become a generic-category `std::error_code`. After every start failure, BackendRunner calls `EbpfBackend::stop()`, and the backend uses local resource flags to clean only resources acquired during partial startup. `EbpfLoaderOps` consumes a private temporary `EbpfLoaderConfig` containing only `iface`, `arena_pages`, and `cleanup_interval_ms`; it may expose `bpf_ctx*` in function signatures, but only inside the private eBPF backend boundary. `EbpfLoaderOps` is a static-storage function table. `EbpfBackend` stores a non-owning pointer or reference to it plus a non-owning `void*` operation context passed to every function. Production may use `nullptr`; tests use fixture-owned contexts for isolated traces and configured results, and the context must outlive the backend. The production and test seam lives in a single private `src/backend/ebpf/ebpf_loader_ops.h` header, so later `env` refactors stay contained inside the eBPF backend boundary. `EbpfBackend` owns current C loader state with `std::unique_ptr<bpf_ctx>` as a transitional measure; `bpf_ctx` and direct operations on it remain refactor targets after the production path runs through the C++ backend boundary. `EbpfBackend` unit tests fake `EbpfLoaderOps` so lifecycle error mapping can be verified without root, BPF attachment, a real interface, BPF arena support, or kernel feature availability. Current C cleanup returns `void`, so Module 7 treats cleanup as successful and defers typed cleanup failure to the later eBPF loader resource/RAII refactor.

**Consequences**

The Host Runtime has one production lifecycle path, so BackendRunner remains the source of lifecycle sequencing and the owner of the runtime loop. `EbpfBackend` performs local resource-safety checks but does not duplicate the full runner state machine or own stop policy; its lifecycle methods are runner-owned hooks, and its destructor does not call `stop()`. Stop sources are represented by `StopCondition` in `src/backend/stop_condition.h`; Process Control directly implements that interface in the MVP while depending only on the stop-condition contract. Process Control keeps static methods for POSIX signal-handler-facing operations, but `BackendRunner::run()` consumes it through the instance `StopCondition` API. Manual and timeout shutdown are also modeled as Stop Requests: Manual means an in-process control source explicitly requested shutdown, while Timeout means a Stop Condition's configured runtime deadline elapsed. Neither reason represents a backend failure, and stop sources never execute backend stop directly. Module 7 defines both reason semantics but does not add production Manual or Timeout Stop Condition implementations. Module 7 keeps production composition in `main.cc`: load Config, install signal handlers, build the selected backend through `make_backend(const Config&)`, construct `BackendRunner`, and call `run(process_control)`. Successful shutdown returns exit code `0` without printing the `ShutdownReport`; operator-facing successful-shutdown diagnostics are deferred. Module 7 keeps the eBPF dataplane runnable while limiting the C++ change to the backend boundary; low-level loader diagnostics can remain in the C boundary temporarily, but operator-facing lifecycle messages belong outside `EbpfBackend`. Unit tests can fake loader operations without root or BPF attachment, while `struct env` remains quarantined in a removable C-loader adapter. Backend-neutral `CacheConfig` is accepted by `EbpfBackend`, but cache fields not expressible through the current C loader are intentionally deferred to the Cache/DNS Module.
