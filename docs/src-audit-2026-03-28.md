# `src/` Code Review Report (Bug / Design / Performance)

Date: 2026-03-28  
Scope: `src/` (BPF + userspace), static review with repository and diagnostics context.

This report focuses on potential issues that are actionable in real network operation, excluding IPv6 feature scope.

## Severity Summary

- High: 3
- Medium: 5
- Low: 4

---

## High Severity Findings

### 1) Cleanup thread shutdown can block up to full interval
- **Location:** `src/core/loader.c:484-537`
- **What:** `cleanup_thread_func()` sleeps with `nanosleep(interval_secs)` and only checks `cleanup_running` after wake. `loader_stop_cleanup_thread()` calls `pthread_join()` directly.
- **Impact:** shutdown/rolling-restart latency can be unexpectedly high (up to configured cleanup interval), hurting operational agility and potentially delaying failover actions.
- **Recommendation:** use condition-variable/eventfd based wakeup for interruptible sleep so stop is near-immediate.

### 2) Event bus is intentionally non-thread-safe and can race if usage expands
- **Location:** `src/runtime/events.h:20-22`, `src/runtime/events.c:21-85`
- **What:** event bus subscriber mutations and publish iteration are unsynchronized.
- **Impact:** currently safe only if call graph remains effectively single-threaded for bus ops; future multi-threaded publish/subscribe can cause races or corrupted subscriber state.
- **Recommendation:** either (a) keep strict single-thread ownership and codify it in architecture docs + tests, or (b) add topic-level lock / RCU-style subscriber snapshot.

### 3) Parser allocates 1500-byte stack buffer per event on hot path
- **Location:** `src/core/dns_parser.c:664`
- **What:** `uint8_t flat_buf[1500];` allocated on stack per ring-buffer event.
- **Impact:** high packet rates plus thread stack constraints can increase pressure and reduce headroom; this is a common hidden tail-latency amplifier.
- **Recommendation:** move to reusable thread-local scratch buffer or bounded arena/workspace object in parser runtime.

## Medium Severity Findings

### 4) Cache map update failure leaves fresh arena content but no index entry
- **Location:** `src/core/dns_parser.c:318-361`
- **What:** arena slot and `slot_owners[idx]` are updated before `bpf_map_update_elem()`. On map update failure, data remains written but unreachable by key.
- **Impact:** correctness is mostly preserved (no stale key served), but write amplification and slot churn increase under repeated map-update failure conditions.
- **Recommendation:** add explicit failure accounting for “arena-write-without-map-link” and consider rollback marker / delayed slot-owner commit.

### 5) Additional-section parse path has mixed reject telemetry behavior
- **Location:** `src/core/dns_parser.c:845-851`
- **What:** some malformed additional-section paths return `0` without reject reason increment.
- **Impact:** visibility blind spots for malformed traffic / parser hardening work; hard to tune protections from metrics.
- **Recommendation:** consistently count parser reject reason in all malformed additional-section exits.

### 6) TCX fallback handling path remains under-specified for non-EOPNOTSUPP failures
- **Location:** `src/core/loader.c:323-334`
- **What:** in-code TODO notes limited error taxonomy for TCX fallback.
- **Impact:** attach behavior under kernel/driver variants may be brittle or noisy.
- **Recommendation:** classify expected attach errors explicitly and metric-tag fallback reason classes.

### 7) Potential lock hold enlargement in cleanup delete loop
- **Location:** `src/core/dns_parser.c:534-562`
- **What:** lock is held per expired key while map lookup+delete path executes.
- **Impact:** under large expired bursts, lock contention can delay concurrent cache insert/update paths.
- **Recommendation:** pre-validate candidates outside lock where possible; keep lock section minimal around slot-owner consistency mutation only.

### 8) Observability endpoint rendering is buffer-capped but silently truncates
- **Location:** `src/core/obs_http.c:37-47`
- **What:** metric append macro clamps writes to buffer capacity without explicit overflow signal.
- **Impact:** at metric cardinality growth, output truncation can occur silently, impairing monitoring trust.
- **Recommendation:** add explicit truncation sentinel metric/log (`shinku_metrics_truncated 1`) and/or dynamic buffer strategy.

## Low Severity Findings

### 9) Narrowing-conversion warnings in parser offsets
- **Location:** diagnostics across `src/core/dns_parser.c` around offset math and `int` parameters.
- **What:** multiple `uint32_t` -> `int` narrowing warnings.
- **Impact:** mostly safe for current packet bounds, but decreases static safety confidence.
- **Recommendation:** normalize offset/length math to `size_t`/`uint32_t` consistently and cast only at API boundaries.

### 10) Verbose stdout/stderr in performance-sensitive operational code paths
- **Location:** `src/core/dns_parser.c:370-377`, `src/core/loader.c` attach/retry logs.
- **What:** frequent logs can add jitter under stress and complicate log SLO budgets.
- **Impact:** modest overhead/noise; can become meaningful under incident floods.
- **Recommendation:** gate high-frequency logs behind level or sampling.

### 11) Exit code normalization in CLI can hide exact internal negatives
- **Location:** `src/cli/main.c:70`
- **What:** returns `-err` for negative errors, collapsing domain-specific error taxonomy into shell codes.
- **Impact:** low, but less expressive for automation diagnostics.
- **Recommendation:** map to stable explicit exit code table.

### 12) Diagnostic false-positive in BPF translation unit
- **Location:** `src/bpf/cache.bpf.c` LSP diagnostics (`typedef redefinition ... vmlinux.h`)
- **What:** known LSP artifact for BPF TU include model; build/test are passing.
- **Impact:** low (tooling noise).
- **Recommendation:** document as known diagnostic caveat and rely on build/test gates for BPF correctness.

## Design / Architecture Notes (Non-bug but important)

1. **Current ECS keying model is now correct for anti-pollution goals** (same-subnet reuse, cross-subnet isolation, `/0` global reuse) and verified by integration tests.
2. **Fail-open behavior is implicit but should be explicit policy** in docs/runbooks: when fast path fails, expected behavior is pass-through with degraded signals.
3. **Capacity policy remains basic ring overwrite + TTL cleanup**; real traffic skew/churn will likely require admission and eviction tuning primitives.

---

## Recommended Fix Order

1. Interruptible cleanup-thread stop path (High)
2. Event bus concurrency contract hardening (High)
3. Parser stack buffer strategy (High)
4. Additional-section reject telemetry completeness (Medium)
5. TCX fallback error taxonomy (Medium)
6. Cleanup lock-window reduction + metrics truncation signaling (Medium)
